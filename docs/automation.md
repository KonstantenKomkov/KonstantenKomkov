# Автоматическое обновление профиля

Workflow `.github/workflows/update-profile.yml` запускается ежедневно в 00:17 UTC
и вручную через `workflow_dispatch`. Он обращается к рабочим репозиториям только
через GitHub REST API, не создаёт их клоны и не использует cache или artifacts.

## Настройка GitHub

В публичном профильном репозитории `<github-login>/<github-login>` задайте variables:

- `IT_ACTIVITY_GITHUB_LOGIN` — публичный login владельца профиля;
- `IT_ACTIVITY_TIMEZONE` — необязательный часовой пояс IANA; без него используется
  `Europe/Moscow`.

Задайте Actions Secrets:

- `IT_ACTIVITY_GITHUB_READ_TOKEN` — отдельный fine-grained PAT только для чтения;
- `IT_ACTIVITY_GITHUB_ADDITIONAL_READ_TOKENS` — необязательные дополнительные
  fine-grained PAT, по одному токену на строку, для приватных репозиториев других
  владельцев ресурсов;
- `IT_ACTIVITY_AUTHOR_EMAILS` — разделённые запятыми авторские email;
- `IT_ACTIVITY_EXPECTED_REPOSITORIES` — разделённые запятыми полные имена всех
  репозиториев, отсутствие доступа к которым должно блокировать публикацию;
- `IT_ACTIVITY_ADDITIONAL_EXPECTED_REPOSITORIES` — необязательное дополнение к
  ожидаемому списку, если исходный Secret нельзя безопасно заменить;
- `IT_ACTIVITY_EXCLUDED_REPOSITORIES` — необязательный приватный список исключений.

Для каждого fine-grained PAT выберите одного владельца ресурсов и минимальный набор
ожидаемых репозиториев этого владельца. Все токены должны быть выпущены настроенным
GitHub-аккаунтом. Разрешите только чтение repository metadata и contents; права
записи токенам сбора не нужны. Если организация требует одобрения или
SSO-авторизации токена, завершите их до ручной проверки workflow.

Основной токен храните в `IT_ACTIVITY_GITHUB_READ_TOKEN`. Токены для остальных
владельцев поместите в один многострочный Secret
`IT_ACTIVITY_GITHUB_ADDITIONAL_READ_TOKENS`, строго по одному токену на непустую
строку. Одинаковые токены и строки с пробелами отклоняются до обращения к GitHub.

GitHub не позволяет прочитать сохранённое значение Secret. Чтобы добавить
обязательные репозитории без замены исходного списка, создайте
`IT_ACTIVITY_ADDITIONAL_EXPECTED_REPOSITORIES`: приложение объединит оба списка и
проверит их целиком. Имена в дополнительном списке также разделяются запятыми.

В настройках Actions разрешите профильному workflow запись contents через штатный
`GITHUB_TOKEN`. Этот токен обслуживает checkout и push только профильного
репозитория; приложению для чтения GitHub API передаётся исключительно отдельный
`IT_ACTIVITY_GITHUB_READ_TOKEN`.

## Безопасное поведение

Перед записью приложение объединяет репозитории, доступные всем настроенным токенам,
и проверяет присутствие полного ожидаемого набора. Противоречивые сведения от разных
токенов блокируют публикацию. Ошибка доступа не раскрывает имя приватного
репозитория, а неполная агрегация не заменяет публичные файлы. Workflow добавляет в
коммит только фиксированные `README.md` и семь файлов из `generated/`; если их
содержимое не изменилось, коммит и push не выполняются.

## Репозитории, доступные только с локальной машины

GitHub-hosted runner не видит клоны на пользовательском Mac. Для репозиториев,
которые нельзя выдать read-only PAT без одобрения организации, выполните тот же
`python -m it_activity generate` локально с `IT_ACTIVITY_LOCAL_REPOSITORIES`.
Формат и гарантии переменной описаны в `docs/configuration.md`.

Локальный запуск должен получать существующие GitHub-настройки и отдельный
read-only PAT через окружение, чтобы объединить локальную историю с уже
учитываемыми API-репозиториями. Приватные значения храните вне рабочего дерева,
с правами только для текущего пользователя; токен предпочтительно держать в
macOS Keychain и добавлять в окружение лишь на время процесса генератора.

Не включайте недоступные локальные репозитории в Actions Secret
`IT_ACTIVITY_ADDITIONAL_EXPECTED_REPOSITORIES`: hosted workflow не сможет их
прочитать и по правилам fail-closed остановится. При локальном запуске их
ожидаемые GitHub-имена или непрозрачные идентификаторы других Git-хостов выводятся
из `origin` автоматически.

Планировщик на Mac следует включать только после формирования полного списка
локальных клонов и контрольного запуска. Иначе корректный fail-closed процесс
опубликует полный API-вклад, но только часть задуманного локального вклада.
